一、全技术栈角度分析（六层）
----------------------------------------------------------------

[1.1] 前端层（Electron 渲染）
  现状：渲染进程通过 eval 执行模块（core-v10.js），主题系统存在「双系统并存」，
        多处永久定时器与全局监听未清理。
  主要问题：
    - 主题双系统冲突：浅色主题下聊天区仍被硬刷成黑底（theme.js:39 + ui-interactions.js:468）。
    - 资源泄漏：notifications.js:224、hud.js:248、canvas-view.js:407-430 的定时器/全局监听
      永不销毁，renderer 重载后叠加，空闲也吃 CPU。
    - 拖拽附件在 contextIsolation 下 require('fs') 为 {}，卡在「正在保存」（ui-interactions.js:4-5,140）。
  对比：KIMI（Web/App 流式顺滑、Artifact 并排、停止醒目）与 QODERWORK（IDE 内联 diff/文件树）
        在流畅度与内联体验上明显领先；本产品补全弹窗侵入、画布/HUD 与对话割裂。

[1.2] 后端层（双后端架构）
  现状：Electron 主进程（web-server.js:8080 + core-v10.js + modules/*）与独立进程
        （server/index.js:3847 + core.js + server/modules/*）是两套平行实现，
        工具/agent/guardrails 各自重复。
  主要问题：
    - 双后端割裂：无单一事实源，行为易漂移；免费搜索强依赖 8080 代理。
    - 单点故障：server/index.js 单进程 in-memory（clients/nodes/pendingCalls 均 Map），
      无 HA、无水平扩展、无消息队列。
    - serveStatic 流无 error handler（server/index.js:184,190），文件被删即进程崩溃。
  对比：KIMI 云端多实例负载均衡自动扩缩；QODERWORK 云端编排 + 工具沙箱隔离 + 超时重试。
        本产品无 HA、工具本地执行、节点无心跳检测死连接（ws-router.js + node-proxy.js:125）。

[1.3] 模型层（多供应商 + 本地兜底）
  现状：云端 API（DeepSeek/硅基/豆包等）+ Ollama 嵌入兜底，resolveCloudModel 路由。
  主要问题：
    - 状态机硬编码 ollama（agent-workflow.js:103,261；agent-handoff.js:67），云端模型选择形同虚设。
    - max_tokens:16384 硬编码（cloud-api.js:391,476），小输出模型（豆包/DeepSeek-chat）直接 400。
    - fallback 到 ollama 时 callCloudAPI 抛「请填 ollama Key」而非优雅降级（cloud-api.js:443 + error-recovery.js:313）。
  对比：KIMI 自研大模型、QODERWORK 专业代码大模型；本产品模型调度鲁棒性弱、缺降级闭环。

[1.4] 工具层（bash/文件/浏览器/搜索）
  现状：bash、文件、浏览器（Playwright）、搜索、知识库检索等工具齐全。
  主要问题：
    - run_command 白名单被 shell 元字符绕过（server/modules/tools.js:172-180；node-agent.js:213）。
    - Playwright 未安装（browser-pro.js:8），JS 渲染抓取与 /browser 长期失效。
    - Python 沙箱过度拦截 os/sys/subprocess（sandbox.js:35），data_analyst 角色被废。
  对比：KIMI/QODERWORK 普遍内置浏览器自动化与受限沙箱；本产品沙箱过严且白名单可被绕过（两端失衡）。

[1.5] 数据层（SQLite + 文件）
  现状：better-sqlite3 + 文件系统，本地知识库 BM25+向量+RRF 检索较强。
  主要问题：
    - 数据目录写死 E:\my-ai-data（main.js:52/69、core-v10.js:359、database.js:43、node-agent.js:41 等），
      非 Windows / 无 E 盘环境直接失效。
    - 普通聊天不注入记忆上下文（memory.js + api.js:349），「记忆」形同摆设。
    - memory 写入缺 created_at（server/modules/memory.js:23），时间衰减失效。
  对比：主流产品记忆与知识检索深度集成；本产品记忆召回链路断裂。

[1.6] 部署层（electron-builder 多平台）
  现状：package.json 已配 win/mac/linux/arm 多目标构建。
  主要问题：
    - 路径写死 E: 导致跨平台构建产物在非 Windows 实际不可用（与「多平台」目标自相矛盾）。
    - Playwright/iconv-lite 等依赖未随包或声明不全，全新 npm install 后功能丢失。
  对比：KIMI/QODERWORK 为云端服务无分发问题；本产品桌面分发受路径/依赖硬编码拖累。

二、功能模块角度分析（盘点）
----------------------------------------------------------------

[2.1] 实质可用模块
  盯盘数据链：market-data.js（pytdx→腾讯→缓存三级降级）、stock-quote.js、market-db.js、market-panel.js
  知识/检索 ：knowledge.js（BM25+向量+RRF）、search.js（代理+付费直连）、crawl-service.js（HTTP 兜底）
  研究/智能 ：deep-research.js、agent-loop.js、skill-generator.js、query-rewriter.js
  工程/集成 ：github.js、image-search.js、voice.js、manga-*、task-queue.js、scheduler.js、guardrails.js
  画布/UI   ：canvas-*、context-panel.js、admin-ui.js、notifications.js、theme.js

[2.2] 半成品 / 未接通模块
  股价预警引擎：watcher.js 监控逻辑存在，但 market-db.js + market-panel.js 中 logAlert 零调用，
                预警面板永远无数据；且 watcher.js:128 把中文名直接喂给需代码数组的 fetchQuotes，监控失效。
  交易日历    ：trading-calendar.js 仅硬编码 2026 节假日，未处理中国调休补班日，无 2025/2027 数据。
  浏览器自动化：browser-pro.js 依赖 Playwright 未装，长期降级/失效。
  邮件        ：office-auto.js 仅实现 SMTP 发信，readEmails 为占位报错，CalDAV 声明与实际不符。

[2.3] 概念级 / 占位模块（planned，无后端）
  IM 接入     ：connectors.js 中微信/钉钉/飞书/Slack/Telegram 全部 status:'planned'。
  邮箱收发    ：仅发信；收信占位；无邮件触发 Agent。
  信息聚合    ：无 RSS/Atom/多源订阅面板；websearch/crawl 存在但无「聚合 feed」。
  网页监控    ：watcher.js 仅有 stock/keyword 两类，无指定 URL 内容变更监控。
  自我进化闭环：仅有 per-task 反思 + 技能推荐，缺「失败→自动改 prompt/策略」闭环。
  云端同步    ：sync-client.js 依赖本地 127.0.0.1:8080，无真实云后端。
  数据连接器  ：MySQL/Redis、Notion/Obsidian/Calendar、Docker/SSH/VSCode 全为 planned。

六、与 KIMI / QODERWORK 对比总结
----------------------------------------------------------------

维度                 本产品                   KIMI                   QODERWORK
──────────────────  ──────────────────────  ─────────────────────  ─────────────────────
架构/扩展            双后端割裂、单进程无HA   云端多实例/负载均衡      云端编排+沙箱隔离
长上下文             预算 6000，无分块         自研大模型+长上下文       代码大模型
深度研究             线性单轮无反思闭环        多轮检索+深度调研          —
代码能力             单次 callAPI，无 diff      —                       AST/多文件/diff/重构
连接器广度           IM/邮箱/数据全 planned    资讯/生态接入             IM/邮箱/数据连接器丰富
浏览器自动化         Playwright 未装失效       内置                    内置
本地知识检索         BM25+向量+RRF（强）      一般                    一般
桌面一体化           任务栏/圆角/面板（强）     Web/App                  IDE 内联
安全模型             contextIsolation（到位）  云端                    云端+沙箱
跨平台自洽           路径写死 E:（不自洽）      无分发问题              无分发问题

结论：
  - 优势项（应保持放大）：本地知识混合检索、桌面一体化体验、安全模型、技能自生成。
  - 最大短板：① 后端架构自洽性（双后端/单点/路径写死）；② 智能体核心鲁棒性
    （上下文截断/max_tokens/状态机硬编码/死循环）；③ 功能模块广度（IM/邮箱/聚合/监控全缺）；
    ④ 依赖与跨平台自洽（Playwright/iconv/路径）。
  - 从「全技术栈可用性」与「功能模块广度」综合看，本产品距 KIMI（通用助手）在长上下文/
    深度研究/云端 HA 差距大；距 QODERWORK（编码助手）在代码多文件编辑/连接器广度/沙箱隔离
    差距大。补齐 B1~B9 与 F1~F12 中的高优项，即可在「本地+桌面+安全」定位上形成差异化反超。
